# Wii Precise Draw Diagnostic Colors Design

## Problem

The first staged hardware diagnostic still reports `C002`. That result rules out exceptions while scene operations are actively committing and while the Wii renderer records overlay capture, frame-plan construction, or GX submission. It leaves two uninstrumented regions: generated draw bookkeeping before the Wii renderer records a stage, and generated post-render counters after the Wii renderer completes and clears its stage.

The background is also identical to the previous build. A stale WBFS can therefore look exactly like a new build when both report `C002`.

## Goal

Produce one new hardware diagnostic that identifies every remaining generated `Core.Draw()` region and assigns a distinct dark background color to every draw diagnostic code. Successful startup remains black, visible code glyphs remain white, and no loader setting or filesystem initialization is added.

## Considered Approaches

### Precise generated-core markers and Wii-owned colors (selected)

Add portable transition markers to the authored C# `Core.Draw()` method immediately before FPS and debug frame-counter calls. Let normal code generation emit those markers into Wii C++, then map them to visible codes in the Wii host. Resolve the background color from the final failure code in the Wii failure-screen presentation layer.

This provides the narrowest result in one hardware build and respects the rule that generated output is never patched.

### Existing-stage mapping only

Map only the generated stages that already exist. This is smaller, but post-render metrics, FPS counting, and debug counting would remain one ambiguous code and could require another hardware build.

### Disable counters one at a time

Disable FPS or debug frame counting and observe whether the failure disappears. This changes runtime behavior before identifying the failing boundary and would be guess-driven rather than diagnostic.

## Diagnostic Codes and Colors

All colors use an opaque alpha channel and dark RGB values so the white code remains readable.

- `C002`, fallback generated draw boundary: orange `{ 0xC0, 0x40, 0x00, 0xFF }`.
- `C101`, scene commit and packaged asset loading: purple `{ 0x60, 0x20, 0x90, 0xFF }`.
- `C102`, Wii 2D overlay capture: blue `{ 0x00, 0x30, 0xA0, 0xFF }`.
- `C103`, Wii frame-plan construction: teal `{ 0x00, 0x70, 0x60, 0xFF }`.
- `C104`, Wii GX submission: magenta `{ 0xA0, 0x00, 0x60, 0xFF }`.
- `C105`, generated draw setup: brown `{ 0x70, 0x30, 0x10, 0xFF }`.
- `C106`, frame-boundary timing and bookkeeping after scene commit: olive `{ 0x60, 0x60, 0x00, 0xFF }`.
- `C107`, render-manager entry or timing wrapper: navy `{ 0x10, 0x20, 0x70, 0xFF }`.
- `C108`, post-render metrics before frame counters: dark cyan `{ 0x00, 0x70, 0x90, 0xFF }`.
- `C109`, FPS render-frame counter: green `{ 0x00, 0x70, 0x20, 0xFF }`.
- `C10A`, debug render-frame counter: violet `{ 0x70, 0x20, 0xA0, 0xFF }`.

Startup and normal runtime presentation remain black. Existing non-draw failure codes retain the current red fallback and are outside this diagnostic cycle.

## Authored Engine Markers

The authored engine file `C:/dev/helworks/helengine/engine/helengine.core/Core.cs` adds two assignments without changing counter behavior:

1. Set `LastSceneTransitionStage` to `BeforeFpsRenderFrame` immediately before `FPSComponent.RecordRenderFrame()`.
2. Set `LastSceneTransitionStage` to `BeforeDebugRenderFrame` immediately before `DebugComponent.RecordRenderFrame()` inside the existing feature guard.

The existing `AfterRenderManager3DDraw` stage already isolates post-render metrics before the new FPS marker. Existing draw-begin, frame-boundary, and before-render-manager stages cover `C105` through `C108`.

Generated C++ is regenerated by the normal Wii build and is never edited directly.

## Wii Failure Refinement

`WiiApplication.RefineDrawFailureCheckpoint()` resolves caught draw exceptions in this order:

1. Active scene-commit stages map to `C101`.
2. A non-`None` `WiiDrawStage` maps to `C102`, `C103`, or `C104` and takes precedence over the broader generated stage.
3. Remaining generated transition stages map to `C105` through `C10A`.
4. Unknown or absent state preserves `C002`.

This ordering preserves the detailed native-stage result when the generated core still reports the broader `BeforeRenderManager3DDraw` boundary.

## Failure Presentation

`WiiFailureScreen` owns a pure code-to-background-color resolver because color selection is presentation behavior. `WiiApplication.ResolvePresentedClearColor()` asks this resolver for the current failure code whenever `FailureActive` is true. The existing persistent loop continues clearing and presenting frames, then writes the white code over both external framebuffers.

The fallback `C002` color changes from red to orange. Seeing red `C002` therefore proves the previous WBFS is still being launched; seeing orange `C002` proves the new build is active even if no refined stage matches.

## Validation

- Add engine tests/source-contract assertions for the authored FPS and debug transition markers.
- Add Wii source-contract tests for `C105` through `C10A`, refinement ordering, and every approved RGB mapping.
- Verify that generated C++ contains both new marker strings after a normal build.
- Build the packaged Wii ISO and derive its matched WBFS.
- Verify both images with WIT and confirm disc ID `RCIE01`, IOS56, and one DATA partition.
- Boot the ISO in Dolphin and confirm scene loading and repeated rendered frames still succeed.
- Boot the WBFS through ordinary USB Loader GX settings and report both the code and background color.

## Non-Goals

- Fixing FPS, debug, timing, or renderer behavior before the precise failing stage is observed.
- Patching generated C++ output.
- Restoring runtime trace files under USB Loader GX.
- Changing USB Loader GX configuration.
- Assigning unique colors to non-draw startup and update codes in this diagnostic cycle.
